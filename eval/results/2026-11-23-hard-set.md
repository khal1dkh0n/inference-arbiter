First scores on `eval/hard_questions.yaml` (draft, 26 cases: 15 executable, 6 reasoning,
2 domain, 3 trap) for a plain mid-tier call, a plain frontier call, and the Phase 3
`execute` mode on the mid tier. Judge `mid`. One run per case unless stated.

`hard_mid_v2_nonexec.json` (tier:mid), `hard_frontier_run1.json` (tier:frontier),
`hard_execute_mid_run3.json` (execute:mid), plus the earlier and comparison runs named

## Phase 3 exit criterion

Build plan: an end-to-end Q&A flow that verifies code or calculations inside an isolated
`sbx` MicroVM with zero host credential exposure and full audit logging in SQLite.

| Part | State | Evidence |
|---|---|---|
| End-to-end flow in an `sbx` MicroVM | Met | `ask --execute` and `execute:<tier>`; 26 of 26 cases ran a program in run 3 |
| Isolation | Met as probed | No host mount, deny-all network rule scoped to the sandbox, run as `nobody` with only `PATH`, `HOME`, `LANG`; opt-in live test `tests/test_sandbox_live.py` (not part of the default suite) |
| Audit logging | Met | `sandbox_runs` table, telemetry schema 7: program text, exit code, output, policy, environment names, removal |
| "Verifies" | Partly | The answer is computed by execution. It is cross-checked only when the model also gives a claim, which it now rarely does (see below) |

## Caveats

- One run per case, 26 cases. One case is about 4 points. The ordering of the three
  strategies rests on which cases a strategy can finish at all, which repeated across
  runs for the mid tier; the one-case differences do not.
- The set is a draft written to stress computation. It shows that running code beats
  working a computation out in the model's reasoning; it does not show execution helps
  on questions that need no computation. `auto` mode does not select `execute`.
- The three trap cases are rubric-graded by the `mid` judge, which is also the answering
  model for tier:mid and execute:mid (3 self-graded verdicts each).
- Two frontier answers (HX-12, HR-10) held the expected value but not in final position
  and were passed by the judge.
- The frontier comparison is at the shipped output limit. A higher limit might answer
  some of the six; it was not tried because of cost.
- `executed` is not `verified`. HX-12 shows a clean run can still be a wrong program.
  Open follow-up: require two independently written programs to agree before an answer
  counts as verified.
- The isolation figures come from the opt-in live test. The gate code and the audit rows
  were reviewed for this write-up; the live probe was not rerun.

## Addendum: two-program cross-check (same day)

`execute.cross_check` (off by default) has two programs written independently from the
question, each run in its own sandbox, and compares their answers in code. Both match:
`verified`. They differ: `disputed`, no answer returned (scored as a fail here). One
failed: `one_sided`, the survivor's answer returned as not cross-checked. The earlier
claim-based status `verified` is renamed `claim_matched` (telemetry schema 8).

All 26 cases, program A on `mid`, free, one run per row. Raw records:
`data/eval/hard_execute_crosscheck_run1.json`, `..._run1_mid_coder32b.json`,
`..._run1_mid_mid.json`.

| Program B | Verified (right) | Disputed | One-sided (right) | Answered right | p50 |
|---|---|---|---|---|---|
| none (run 3 above) | n/a | n/a | n/a | 25 | 17.3 s |
| `code` (qwen3 14b) | 6 (6) | 18 | 2 (2) | 8 | 23.3 s |
| qwen2.5-coder:32b | 9 (9) | 12 | 5 (5) | 14 | 34.5 s |
| `mid`, asked for a different method | 22 (22) | 3 | 1 (1) | 23 | 27.0 s |

- No `verified` answer was wrong: 37 of 37 across the three runs.
- HX-12, the wrong answer in run 3, was `disputed` in all three runs.
- The local second models dispute correct answers. Per-program grading from the run
  output (not recomputed here): in the 24 gradable disputes of the two local-model runs
  program A was right in 23 and program B in none.
- `mid`+`mid` disputes: HX-12, HT-05 and HT-06; HR-10 was one-sided. The two trap
  disputes look like the same conclusion in different words, which exact string
  comparison does not accept (read from the run output, not checked case by case).
  Open follow-up.
- Follow-up closed in run 2 (`data/eval/hard_execute_crosscheck_run2_mid_mid.json`,
  figures recomputed from its records). Checked case by case first: in run 1 HT-05
  printed `No amount posted: malformed message` against `Malformed message` and HT-06
  `No` against `No: it returns [-3333, ...]`, the same conclusion both times. Both
  programs' prompts now carry one fixed rule for the last line (bare value; exactly
  `Yes` or `No` for a confirm question; exactly `None` when the value does not exist);
  the comparison is unchanged. Run 2, `mid`+`mid`, 26 cases, free: 24 verified (24
  right), 1 disputed, 1 one-sided (right), 0 failed; 25 answered right; p50 32.2 s, p95
  47.5 s (run 1: 27.0 s, 49.9 s). HT-05 verified on `None`, HT-06 on `No`, HT-04 on
  `0`; HX-12 disputed again (A 7466, B 25775); HR-10 one-sided again (program B's
  draft call returned invalid output). The three trap cases are rubric-graded by the
  `mid` judge, the same model that wrote the programs.
- Shipped `cross_check_tier` is `mid`. Its known weakness: two drafts from one model can
  share a misreading. This set did not show one, and one run per case cannot rule it out.
