# Mcp mode, first run with a live model, 2026-11-24 (3 cases)

Mcp mode serves the documents of one folder through the read-only documents server
behind the tool gate. One model call writes a tool plan from the question and the
document names and sizes; code carries the plan out; the documents that were read go to
the same grounded pipeline as `openbook`. Until this run the mode had only been exercised
with fake model clients. This file records the first run with a live model. It is a
smoke run: three cases, one run each. It shows that the path works and what one failure
looks like. It does not give a rate for anything.

## Setup

- Suite `openbook`, strategy `mcp`, cases OB-01 (single document lookup), OB-20 (answer
  split over two of three documents) and OB-U3 (unanswerable, two documents).
- Plan and draft on `mid` (kimi-k3.1-pro:cloud).
- Two settings differ from the shipped config, to keep the run on free tiers: the
  grounding verifier was `ground_chat` (qwen3 14b, local) through `--verifier-tier`, and
  `openbook.escalation_tier` was set to `mid` in a copy of the config, which switches the
  escalation call off. No case reached a state that escalates under the shipped config
  either: one was grounded and two abstained.
- Every model call went to the `ollama` provider and is logged at 0 USD; calls to the
  Ollama cloud model have no price configured, so that figure is not the cost on a paid
  Ollama plan.
- Raw records are in `data/eval/` (git-ignored): `mcp_smoke.json` and the telemetry
  database `telemetry_mcp_smoke.db`. Every figure here was read from those records.

## Result

| Case | Documents listed | Documents read | Tool calls (plan / code) | Refused | Grounding | Grade | Latency |
|---|---|---|---|---|---|---|---|
| OB-01 | 1 | 1 | 1 / 2 | 0 | grounded | pass | 58.8 s |
| OB-20 | 3 | 2 | 2 / 2 | 0 | ungrounded, abstained | fail | 46.1 s |
| OB-U3 | 2 | 2 | 2 / 2 | 0 | ungrounded, abstained | pass | 30.3 s |

- Model calls: 9 in all. Per case one `plan` and one `draft` call on `mid` and one
  `ground` call on `ground_chat`. 6 calls to the cloud model, 3 local.
- `plan_status` was `ok` in all three cases. The plan calls took 1.8 s, 2.1 s and 2.5 s.
- The gate saw 11 tool calls and refused none. Every planned call named a listed
  document with arguments of the right shape. Each tool call took under 7 ms.
- `tool_server_stopped` was true in all three cases.
- OB-01: the answer is right, its citation is valid and it cites the evidence passage.
- OB-U3: the run abstained, which is the correct outcome for an unanswerable case.

## The failure: OB-20

The question needs `auto-router.md` for the name of the pipeline stage and
`jev-router.md` for the field that reports the tier cap. `router-metadata.md` is in the
folder as an on-topic distractor. The plan read `auto-router.md` and
`router-metadata.md` and left `jev-router.md` unread. The passage that holds the field
was therefore never retrieved, the drafter reported that the passages do not answer the
question, and the run ended with the fixed abstention sentence.

So a plan that picks documents from their names and sizes alone can leave out the one
that holds the answer. The outcome is a wrong abstention, not a wrong answer. The same
case passed under `openbook`, which reads every source it is given
(`2026-11-22-phase2-openbook.md`).

## Limits

- Three cases, one run each. How often a plan leaves out a needed document is not
  measured.
- The grounding verifier was the local alternative, not the shipped `ground_jev`.
- No case had a refused call, a failed plan call or a plan over the cap, so rows 1 to 7
  of the `decide_plan` table were still exercised by tests only.
- The run says nothing about the large corpus, which is out of reach for this mode.
